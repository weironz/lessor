# 设计方案与开发计划

本文回答三个问题：**为什么要造**（现有工具为什么都不行）、**两个纠结点怎么定**
（要不要 Web + 桌面双端；前后端一体还是分离）、**接下来怎么走**（里程碑与验收判据）。

系统本身长什么样见 [architecture.md](architecture.md)，本文不重复。

两个决策各由三个独立视角评审过（现场交付工程师 / 长期维护成本 / 产品定位；
部署运维 / 安全攻击面 / 演进灵活性），结论、最强反方论点和**翻盘条件**都如实记录 ——
翻盘条件成立时就该重审，而不是把决策当教条。

## 一、背景与目标

**产品定位：通用 DHCP 服务器。企业级常驻是核心能力，分阶段达成。**
起点是一个很具体的现场需求，但要做就做好 —— 不做一个只能陪笔记本出差的小工具。

**起点需求**：交付 NVIDIA B300 GPU 服务器和通算服务器，第一步拿 Windows 11
笔记本直连 BMC 网口，立刻发地址、立刻看到 MAC↔IP。

后续的"点进 BMC 页 → 改静态 → 确认新地址通"属于交付专用的尾环，**暂缓**：
先把通用能力做扎实，观察它是否作为附带能力自然获得 —— 租约表里放一个指向
`http://<租约IP>` 的链接本来就近乎零成本，不值得为它立里程碑。

**同一个二进制、两种运行形态**：

| 形态 | 场景 | 行为差异 |
| --- | --- | --- |
| 现场（field） | 笔记本直连 BMC、装机网段、隔离网络 | 默认 ephemeral 租约；`--open` / 桌面壳；关了就走，不留痕 |
| 常驻（resident） | 机房 / 企业网长期服务 | 持久化默认开；注册为系统服务；认证必选；可观测 |

**衍生场景**：装机网段的 PXE / HTTP Boot / iPXE 网络引导（三类客户端已实测）。

**非目标**（收窄后只剩两条）：完整 DNS 服务器（DDNS 联动在远期路线图上）；
DHCPv6 不在当前阶段 —— 列入 v1.x 路线图，不再当"永久非目标"。

## 二、现状调研：为什么要造

逐个看过，没有一个能站住"Windows 11 笔记本上的现场 DHCP"这个位置：

| 方案 | 为什么不行 |
| --- | --- |
| ISC DHCP | 2022-10 官方 EOL。无 Windows 版；配置文件 + root + 常驻形态，与现场场景全不搭 |
| Kea | 官方明确不支持 Windows（仅 Linux/UNIX）。多进程 + JSON 配置 + 数据库钩子，为常驻设计；WSL2 迂回要过 NAT，DHCP 广播根本进不来 |
| dnsmasq | 能力上最接近（DHCP+TFTP+ProxyDHCP 一把抓），**但没有原生 Windows 移植** —— 对的工具存在，却不在现场笔记本跑的那个 OS 上 |
| Windows Server DHCP 角色 | 只存在于 Server SKU，Win11 客户端装不了 |
| tftpd64 | GUI + INI 老工具，无 CLI/API 不可脚本化，DHCP 选项交互简陋，无 HTTP Boot，唯一"可见性"是滚动日志 |
| Serva | 闭源，Community 版有商用限制，同样 GUI-only 无法进流水线 |
| Open DHCP Server | 维护接近停摆，租约可见性只有日志，无现代网络引导支持 |
| dora（Rust） | 仍在维护（2026-05 有提交）但**全库搜不到 `windows` / `target_os`**，依赖 `unix-udp-sock` 和 `pnet`，定位 Linux 常驻（sqlite 租约库、/var/lib 路径） |
| coredhcp（Go） | 插件框架而非成品，"开箱一切皆无"，README 自称 WIP，Windows 支持弱 |
| 手机热点 / Windows ICS | BMC 是 RJ45 口热点接不上；ICS 硬编码 192.168.137.1/24 改地址要动注册表，DHCP 选项零控制，没有租约界面只能 `arp -a` 猜 —— 正是这套土办法的痛催生了本项目 |

**空档**：一个 Windows 11 原生、单文件免安装、普通权限就能跑的现场 DHCP ——
选网卡就开始发地址、MAC↔IP 实时可见、一键进 BMC 页，顺带把 PXE/iPXE/HTTP Boot
接住，且可脚本化。成熟实现全押在 Linux 常驻形态，Windows 上只剩 EOL 品、
老 GUI 工具和不可控的土办法。

常驻方向要诚实：**Linux 数据中心的常驻 DHCP 上，Kea 是强现任**，lessor
不在那里正面硬碰。差异化路线是 —— Windows 也能常驻（Kea 官方不支持）、
单二进制内嵌 UI（Kea 是多进程 + 外置控制面）、以及"现场到常驻是同一个
工具的两种形态"这个连续体（用 Kea 的话，现场那半根本不存在）。

## 二点五、工作量评估：把 Kea 拉下来量了一遍

"做一个 DHCP 服务器难不难"值得用数字回答。把 isc-projects/kea 浅克隆到本地
实测（2026-08-19 的 HEAD）：

| | Kea | lessor |
| --- | --- | --- |
| 产品代码 | **516,947** 行 C++ | **5,868** 行（Rust 4,742 + 前端 817 + 桌面壳 309） |
| 测试代码 | 585,904 行（比产品还多） | 含在上面（129 个测试） |
| 借用的编解码层 | 自带 `lib/dhcp` 33,553 行 | dhcproto 7,216 行（现成 crate） |

拆开看，这 51.7 万行就是"企业级常驻"四个字的真实分量。既然把常驻定为
核心能力，其中相当一部分（持久化、运维接口、HA）就是我们迟早要抵达的领地 ——
**Kea 是这条路的天花板参照，不该被小看**。

| Kea 子系统 | 行数 | 对 lessor 意味着 |
| --- | --- | --- |
| `bin/dhcp4`（v4 应答机本体） | 33,605 | M0–M3 已用 2,052 行覆盖现场子集 |
| `lib/dhcpsrv`（租约库、host 管理） | 71,730 | M5 持久化的领地，sqlite 起步 |
| `hooks/dhcp`（HA/RADIUS/运维命令） | 150,093 | v1.0+ 路线图（HA），分阶段 |
| `bin/dhcp6` | 33,612 | v1.x 路线图 |
| `bin/d2` + `lib/dns`（DDNS） | 43,516 | 远期；完整 DNS 仍是非目标 |
| `netconf` + `yang` + `lib/eval` | 35,540 | 用 API-first 配置与 option 匹配替代 |

工作量可控靠两件事：

1. **分阶段**：现场形态先交付价值（M0–M3 已完成并被五种真实客户端实测），
   常驻能力按 M4–M6 → v1.0+ 逐层长出来 —— 不需要第一天就是 Kea。
2. **站在生态肩上**：dhcproto / tokio / axum / sqlite 省掉了 Kea 自带的底层
   （asiolink 8.2k、http 11k、编解码 33.5k……），同等能力的 Rust 实现
   预期显著小于逐行对照。

诚实的差距也要认：Kea 那 58.6 万行测试代表的成熟度不是行数能追平的，
是年头和真实部署喂出来的。所以路线图把 HA 这类重能力放在最后、以真实需求
触发，并且全程拿 Kea 当行为参照与测试用例矿。

**Kea 怎么用**：当参照物，不当底座。

- **行为参照**：拿不准边缘情况该回什么时，看 Kea / dnsmasq 怎么做。这个方法
  已经赢过一次 —— option 60/43 那个 bug 就是对照 MAAS 生成的 dhcpd.conf
  才破的案（[debugging-pxe.md](debugging-pxe.md) 的"找一个已知能用的参照"）。
- **测试用例矿**：Kea 那 58.6 万行测试沉淀了二十多年的边缘场景，做 M5–M7
  （冲突检测、持久化）时去翻它对应模块的测试目录，比自己凭空想全面。
- **文档**：Kea ARM 对各 option 语义的解释是最好的免费资料之一。
- **不移植代码**：C++/常驻架构与本项目的语言和形态都不匹配 —— 把它的架构
  搬过来，等于把我们刻意避开的复杂度请回来。

### Kea 为什么不做 Windows、UI 为什么在体外

这两个"为什么"值得单独记下 —— 它们解释了空档为什么是结构性的、短期不会被 ISC 填上。

**不做 Windows 是三层原因叠加的**：

1. **技术根**：Kea 官方定位就是"任何 POSIX 兼容系统"。整套形态是 Unix 的 ——
   多进程 daemon（dhcp4/dhcp6/ddns/ctrl-agent 各一个）、控制通道是 Unix domain
   socket、keactrl shell 脚本管进程；底层收发用 raw socket（Linux LPF / BSD BPF），
   而 Windows 从 XP SP2 起阉割了原生 raw socket，要等价实现只能上 Npcap/NDIS
   驱动这个深坑。lessor 在 Windows 上绕开它的方式（绑具体地址 + 广播应答，实测
   受限广播会投递）正是这道移植墙的另一侧。
2. **组织与成本**：ISC 是小型非营利，且有明确前科 —— BIND 9 曾支持 Windows，
   2021-04 宣布弃用、9.18 起彻底移除，官方理由：VS 不支持其依赖的 C11 特性、
   **没有任何开发者用 Windows**、向付费支持客户征询后**收到零个保留请求**、
   还有 WSL2 可用。Kea 从 BIND 10 遗产起家，第一天就没做 Windows。
3. **市场**：Windows 企业环境的 DHCP 位置被微软自家 Windows Server DHCP
   （AD 集成、许可内免费）占死，ISC 的付费客户全是 Linux 基础设施 ——
   投入产出为负。但微软只占了 Server SKU：**Win11 客户端 + 现场场景无人服务**，
   这正是 lessor 的入口。

**UI 不是没有，是拆成了独立的集中管理平面**：Kea daemon 本体零 UI，配置是
JSON 文件 + REST 控制通道（kea-ctrl-agent）；ISC 另有开源产品 **Stork** ——
server-agent 架构，每台 Kea 机器装 stork-agent，中央 stork-server + PostgreSQL
+ Web 界面，集成 Prometheus/Grafana。他们的用户是"管一群 DHCP 服务器的运维
团队"，UI 的自然形态是中央控制台，不是每实例一个网页。

**对本方案的两条印证**：

- Windows 空档是技术（raw socket 层）、组织（ISC 无人用 Windows）、市场
  （微软占位但不覆盖客户端 SKU）三重叠加的结构性空档 —— 其中技术那层
  lessor 已实测解决。
- Stork 恰好是决策二翻盘条件的参考实现：**当产品变成"管一群实例"时 UI 才
  拆出去**（server-agent 形态）；单实例阶段内嵌 UI 是对的。真到那一步，
  照着 Kea + Stork 的形态拆即可。

## 三、决策一：要不要 Web 端 + 桌面端

**结论：都要，但只写一份 UI。** Web 界面（嵌在 lessord 里）是本体，
桌面端只是加载同一份页面的 Tauri 外壳（attach-first：先连已运行的服务，
连不上才拉起自带的 lessord 子进程）。

三个视角的裁决要点：

- **现场交付工程师**：闭环的硬需求是"双击 → 选网卡 → 插线 → 看到 MAC↔IP →
  点进 BMC 页"，桌面端解决的是**可发现性**（不需要工程师知道去浏览器输
  `localhost:8080`）和**生命周期**（关窗即停，不留流氓 DHCP）。
- **长期维护成本**：真正的成本大头是第二套 UI 实现，而不是外壳本身。
  外壳约两百行、增量近零；但 Tauri/bun 工具链、各 OS 打包签名、webview
  兼容矩阵是每个版本都要付的税 —— 所以只承诺维护**一份** UI。
- **产品定位**：立两条红线 —— **禁止出现第二套 UI 实现，禁止任何仅桌面端可用
  的功能**。所有功能走 lessord 的 HTTP/WS API，桌面端永远只是客户端。

**被评审提出的挑战方案**（两个视角独立提出，值得认真对待）：
`lessord --open` —— 启动时自动打开默认浏览器指向本机控制台，配合前台 Ctrl-C
即停。这能以近零成本满足"可发现性"。处置：**做进 M4**，与桌面端并存，
由现场数据裁决。

**翻盘条件**（成立即重审桌面端）：现场验证表明 `--open` + 前台运行的纯 Web
形态无人抱怨找不到页面、无残留服务事故；或出现外壳专属 bug 面、Tauri
大版本迁移成本失衡。

## 四、决策二：前后端一体还是分离

**结论：前后端一体。** 前端构建产物经 rust-embed 打进 lessord，交付物是
单二进制单进程；接口地址全用相对路径。三个视角**一致**推荐一体：

- **部署运维**：现场形态是"一个文件拷进 U 盘，到断网笔记本上双击就跑"。
  一体让**版本漂移在结构上不可能发生** —— 不存在"界面说前端的话、服务说
  后端的话"这种现场没法排查的错位。分离则多一个进程、一个端口、一份配置、
  一种启动顺序问题。
- **安全攻击面**：同源免 CORS —— 管理接口**刻意不发任何 CORS 头**
  （发了就等于允许任意网页读它）；分离方案则被迫开 CORS、多一个 HTTP
  服务面。加固义务（进 M5）：管理 API 与 WebSocket 校验 Host/Origin 头，
  防 DNS rebinding 把恶意网页引到 localhost API。
- **演进灵活性**：分离的**逃生门始终存在且很便宜** —— 系统边界是 HTTP/WS
  API 而不是进程边界，真要拆时删掉十几行的 `ui.rs`、把 dist 静态托管即可，
  不牵动任何决策核心。一体化不锁死任何演进选项。

**翻盘条件**：产品定位漂移成"集中管理平台"（头节点 agent + 中央控制台、
每广播域一个无 UI 实例）时，per-instance UI 失去意义，届时按 API 边界拆分。

**常驻成为核心能力是否触发上面的翻盘条件？** 不触发。常驻的单实例服务带
内嵌 UI 依然成立（从家用路由器到 Proxmox 都是这个形态）；触发拆分的仍是
"集中管理平台"（中央控制台 + 多个无头实例）那一步。

**桌面端与一体的矛盾如何化解**：attach-first。服务已在跑（系统服务/远程机器）
→ 桌面端纯客户端，不碰别人的进程；没在跑 → 拉起自带实例，正常关窗显式带走、
强杀由 Windows Job Object 内核兜底（两条路径都已实测）。"自包含"因此只是
启动器行为，不是架构。

## 五、技术栈（要点）

选型细节与理由见 [architecture.md](architecture.md#技术选型)，这里只记决策性的几条：

- **dhcproto 只当字节层**，分配优先级 / 租约状态机 / 应答决策全部自研 ——
  这层是决策逻辑不是编解码，且已知两处要绕的坑（`set_fname_str` 超 128 字节
  panic、option 93 枚举名照搬注册表容易看懵）都在文档里。
- **不基于 dora 改**：无 Windows 支持是硬性的，而 Windows 正是本项目的第一现场。
  复用它省的是 IO 层，要重写的恰是其架构核心。
- **UI 走 Web + Tauri 外壳**，不走 egui/iced 原生 GUI：原生路线要把界面写两遍
  （远程访问仍需 Web），与"可远程可常驻"形态冲突。
- 实测产物：前端 dist 57 KB（gzip 19 KB）、`lessord.exe` 2.6 MB（界面已含）、
  NSIS 安装包 2.6 MB、桌面外壳 8.7 MB。

## 六、安全红线（设计义务，不是可选项）

DHCP 是天生高危的服务 —— 插错网口、忘了关，都可能污染别人的网段。
开发过程中它真的应答过另一个网段上的 MAAS（未隔离时），所以这些是红线：

1. **收包隔离缺省开启**：Windows 绑具体网卡地址、Linux 要求 `--iface`；
   做不到隔离（macOS、Linux 未给网卡名）时启动即告警，`isolated` 字段如实上报。
2. **同段已有 DHCP 服务器时告警**（M7）：检测到别人的 OFFER/服务器就在 UI
   和日志里大字提示，现场默认不抢答。
3. **OFFER 前冲突探测**（M7）：候选地址先 ARP/UDP 探测，已被占用就跳过并记录。
4. **不留无人管的实例**：桌面端子进程正常关窗显式回收 + Job Object 内核兜底；
   纯 Web 形态提供空闲自动退出选项（M8）。
5. **管理接口最小暴露**：默认只听 127.0.0.1；不发 CORS 头；M5 加 Host/Origin
   校验；开放 0.0.0.0 必须显式配置并在文档标为危险操作。
6. **写操作 API 必须先有认证**（M5 硬性门槛）：作用域 CRUD 落地之前，
   token（或等价机制）+ Origin 校验必须先在 —— 不认证的可写接口不允许存在。

## 七、与 MAAS 的分工边界

32 台 B300 的交付链里两者同时在场，边界必须一页纸说清：

- **lessor 管**：上架第一步（笔记本直连 BMC 发地址、改静态）；MAAS 不在场的
  轻量网启（单台救机、隔离实验网段）；已配静态 IP 设备的发现（RMCP/邻居表）。
- **MAAS 管**：批量装机的全部（commissioning、部署、电源控制），其 dhcpd
  是装机网段唯一的 DHCP。
- **红线**：同一个广播域里两边不同时开 DHCP。lessor 接入已有装机网段前，
  M7 的"检测到其他 DHCP 服务器"告警就是这道闸。

### 成功指标（可度量）

现场形态：

- 插线 → 租约出现在界面：**≤ 10 秒**
- 双击 exe → 看到 MAC↔IP：**≤ 1 分钟**（含选网卡）
- 全程零管理员权限、零安装、零外网依赖

常驻形态（M5/M6 验收）：

- kill -9 / 断电重启后租约**零丢失**，客户端续租不遭 NAK
- 周级连续运行无泄漏、无重启
- 配置变更全部在线生效，无需重启进程

### 未决事项（立项要一并拍板）

- **代码签名证书**：客户现场笔记本可能有 EDR/SmartScreen 策略，未签名 exe
  进不了场。一次性成本，建议 v0.1 前解决。
- **维护 owner 与 plan B**：目前单人开发。若停止投入，现场退路是
  "Linux 盒子跑 dnsmasq"或 tftpd64；常驻退路是 Kea（Linux）。
- **供应链**：cargo audit/deny 进 CI、发布物 SBOM —— 面向企业客户交付时补。
